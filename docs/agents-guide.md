# LLM Agents Guide

**IMPORTANT**: At NO circumstances should you ever modify this file. If you find discrepancies, tell the user instead of modifying yourself unless given explicit clearance. Notify the user instead, as a simple FYI instead of making it a big thing.

Do not open any documentation files unless you think it is relevant. There is plenty of documentation and you might drown yourself in unnecessary context.

## Roles

As an AI agent, your job scope will be limited to a small subset of this repo. This monorepo contains both firmware and the dashboard, as well as documentation. Your primary task will most likely fall to be one of the two:

### 1. Firmware engineer
If the task at hand mentions firmware, you should ignore any thought of the dashboard. Your focus will be mainly C++ code available at `firmware/`. It is absolutely essential to look at the [hardware documentation](hardware.md) first. DO NOT edit this documentation because it relies on human testing and input. At times, there might be references to the dashboard. Refer to its documentation too if necessary.

### 2. Full-stack web developer
If the task at hand mentions the dashboard, you should ignore any thought of firmware. Your focus will be mainly TypeScript code available at `dashboard/`. References to the database should be looked up to [the documentation](llm-generated/database.md). You are free to edit this documentation. 

## Context and Documentation

Your context is limited in the codebase. This is a very large monorepo, with many lines of code and documentation. It is best practice to not immediately open any documentation files unless you think it is relevant. Only open documentation files when you are going to work on that specific part. Do not open them if you are not going to work on it.

Humans however, are not limited in a similar way. Which is why, you MUST write and document everything you do. Every subsystem should be documented in `docs/llm-generated/`. Do not put any documentation written by you outside of that directory. Follow the existing format, where you must ALWAYS add a footer as such:

```
---
Content generated by `provider/model-name` in `harness`.
```

Do not look up other documentation just to see the format. The only thing necessary is this footer.

Your users are students. It would help us if you were to be particularly astute with your documentation and descriptive. Keep minimal word garnish. Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning." Instead of "this point still matters," they write "this point earns its keep." The phrases exist to display the writer, not to convey the idea, and readers can tell. That is why mannered prose irritates: it makes the reader work harder so the writer can perform. It is also imprecise. Metaphors drag in connotations the writer did not choose and cannot control. The fix is to say what you mean. When a literal phrase is available, use it. **You must remove all mannered prose from your written documentation.**

Besides documentation, if you were to go into plan mode, and wish to write (or have written) an extensive plan, copy it to `docs/llm-generated/` for reference. Once the plan is done, write down below the model written footer that it has been acted upon.
