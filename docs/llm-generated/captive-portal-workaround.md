# Project Plan: Headless Captive Portal Authentication for WT32-ETH01

## 1. What Are We Doing?

**Goal:** Enable the WT32-ETH01 to automatically authenticate itself to a university wired network that uses a **captive portal**.

**Problem:** The ESP32 has an IP address on the wired network but cannot reach external resources (e.g., `ping 1.1.1.1` fails) because the network intercepts all traffic and redirects to a login page. The ESP32 cannot display a web page to the user for manual login.

**Solution:** The WT32-ETH01 will act as a **headless captive portal client**. It will use its onboard Wi-Fi to create a temporary configuration AP. The user connects to this AP, enters their university credentials on a simple web page served by the ESP32, and the ESP32 then performs the captive portal login over its **Ethernet interface** on the user's behalf.

## 2. How Can We Do It?

### 2.1 Hardware Platform: WT32-ETH01

The WT32-ETH01 is an ESP32-based board with an integrated **LAN8720 Ethernet PHY**[reference:0].

| Component | Details |
|-----------|---------|
| **Chip** | ESP32 with integrated Ethernet MAC (EMAC) |
| **PHY** | LAN8720 |
| **PHY Power** | GPIO 16 (active high) |
| **MDC** | GPIO 23 |
| **MDIO** | GPIO 18 |
| **PHY Address** | 1 |

**Critical Constraint:** GPIO 0 is used for the Ethernet clock on this board. The BOOT button factory reset is **not available**. Use `esptool.py erase_flash` or the serial console to reset firmware[reference:1].

**Critical Constraint (RMII Clock):** If Wi-Fi and Ethernet are used **simultaneously**, the RMII clock **cannot** be generated by the ESP32's internal APLL clock, as this would cause clock instability. You **must** use an external clock source or external PHY to provide the 50 MHz reference clock[reference:2]. The WT32-ETH01 uses the LAN8720's external clock, so this constraint is satisfied.

### 2.2 Software Architecture

The firmware will have two network interfaces running simultaneously:

| Interface | Role | Purpose |
|-----------|------|---------|
| **Ethernet** | Uplink | Connects to the university wired network; performs captive portal authentication |
| **Wi-Fi (SoftAP)** | Management | Creates a temporary AP for the user to enter credentials and monitor status |

**Data Flow:**
1. **Boot**: ESP32 initializes Ethernet and obtains an IP via DHCP. The port is in a "walled garden" (only DHCP and DNS work).
2. **Wi-Fi AP**: ESP32 starts a SoftAP (e.g., `ESP32-Setup`).
3. **User Interaction**: User connects to the AP, opens a browser, and is served a configuration page.
4. **Credential Submission**: User enters university username/password.
5. **Portal Relay**: ESP32 uses `esp_http_client` over the **Ethernet interface** to:
   - Trigger the captive portal redirect.
   - Fetch the login page.
   - Extract any hidden fields (e.g., CSRF tokens).
   - POST the credentials to the portal's authentication endpoint.
   - Follow redirects and detect success (e.g., by checking if an external site is reachable without redirect).
6. **Confirmation**: ESP32 notifies the user of success (via the web page or an LED) and optionally shuts down the Wi-Fi AP.

### 2.3 Key Challenges

| Challenge | Mitigation |
|-----------|------------|
| **HTTPS portals** | Use `mbedTLS` with `setInsecure()` or embed the CA certificate. Reduce Wi-Fi buffer sizes to free RAM. |
| **JavaScript-generated forms** | Reverse-engineer the JavaScript's API calls from browser dev tools and replicate them in `esp_http_client`. |
| **CSRF tokens / session cookies** | Enable cookie handling in `esp_http_client`. Parse the HTML login page to extract hidden form fields. |
| **Multi-step authentication** | Map the full redirect chain from browser dev tools and replicate each step. |
| **Simultaneous Wi-Fi + Ethernet** | Ensure the RMII clock is provided externally (the WT32-ETH01's LAN8720 does this). |

## 4. Step-by-Step Guidance

### Phase 1: Reverse-Engineer the Captive Portal

**Objective:** Understand exactly how the university's portal works before writing any firmware.

1. Plug a laptop into the wired Ethernet port.
2. Open a browser and navigate to any HTTP site (e.g., `http://example.com`).
3. Open **Developer Tools** (F12) → **Network** tab.
4. Record the following:
   - **Initial redirect URL** (e.g., `http://portal.university.edu/login`).
   - **Form `action` URL** (where credentials are POSTed).
   - **`name` attributes** of the username and password fields.
   - **Hidden form fields** (e.g., `csrf_token`, `session_id`, `redirect_url`).
   - **Cookie names** set by the portal.
   - **Redirect chain** after successful login.
5. Save the HTML of the login page (right-click → "Save Page As") for offline parsing.

### Phase 2: Set Up the Development Environment

**Objective:** Get a working ESP-IDF or Arduino project that compiles for the WT32-ETH01.

1. Install **ESP-IDF** (v5.x recommended) or **Arduino IDE** with ESP32 board support.
2. For Arduino: Install the **AsyncWebServer_WT32_ETH01** library via Library Manager.
3. For ESP-IDF: Add the **MycilaESPConnect** component or clone the repository.
4. Create a new project and configure the Ethernet PHY settings:
   - PHY Type: `LAN8720`
   - PHY Address: `1`
   - MDC Pin: `23`
   - MDIO Pin: `18`
   - Power Pin: `16`
5. Verify that Ethernet initializes and obtains an IP address (use DHCP).
6. Verify that Wi-Fi SoftAP can start **simultaneously** with Ethernet.

### Phase 3: Build the HTTP Client (Ethernet Side)

**Objective:** Fetch the portal login page and extract form fields.

1. Use `esp_http_client` (ESP-IDF) or `HTTPClient` (Arduino) with the **Ethernet interface**.
2. Configure the client to:
   - Follow redirects (`max_redirection_count`).
   - Enable cookies (`HTTP_EVENT_ON_HEADER` callback).
   - Handle HTTPS (use `setInsecure()` for testing, then embed CA cert).
3. Perform a GET request to the initial redirect URL.
4. Parse the returned HTML to extract:
   - Form `action` URL.
   - All `<input>` field names and values (especially hidden fields).
5. Print the extracted fields to serial for debugging.

### Phase 4: Build the Web Server (Wi-Fi AP Side)

**Objective:** Serve a configuration page to the user.

1. Start a SoftAP with a recognizable SSID (e.g., `ESP32-Setup`).
2. Use **AsyncWebServer_WT32_ETH01** to serve an HTML page with:
   - A form for university username and password.
   - A status indicator (e.g., "Connecting...", "Authenticated", "Failed").
3. On form submission, call the HTTP client functions from Phase 3.
4. Return the authentication result to the user (success or failure message).

### Phase 5: Implement the Portal Relay Logic

**Objective:** Perform the captive portal login over Ethernet.

1. **Trigger Redirect:** Make an HTTP request to a known external site (e.g., `http://example.com`) over Ethernet. Capture the 302 redirect to the portal.
2. **Fetch Login Page:** GET the portal login page. Parse and store:
   - CSRF token (if present).
   - Session cookie.
   - Any other hidden fields.
3. **Submit Credentials:** POST the username, password, and all hidden fields to the form `action` URL.
4. **Handle Response:** Follow redirects. Check for a success page or an error message.
5. **Verify Success:** Attempt to reach an external site (e.g., `http://example.com`) without being redirected. If successful, the port is authenticated.

### Phase 6: Test and Refine

**Objective:** Validate the full workflow and handle edge cases.

1. Test with the actual university network.
2. If HTTPS fails, reduce Wi-Fi buffer sizes or increase `mbedTLS` memory allocation.
3. If JavaScript is required, reverse-engineer the API calls and replicate them.
4. Add error handling for:
   - Wrong credentials.
   - Network timeouts.
   - Portal page changes.
5. Add visual feedback (LED) for connection status.
