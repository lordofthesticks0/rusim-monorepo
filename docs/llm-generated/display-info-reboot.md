# /info Reboot: Heap-Walk Hang on `display-v9`

Date: 2026-10-15. Status: trigger removed, root cause (heap corruption) still open.

## Symptom

Opening the info tab rebooted the board. Serial showed `Interrupt wdt timeout
on CPU1`, followed by `Re-entered core dump!` (the crash handler faulting while
writing the core dump) and a reboot. The login bypass (`IS_DEBUG=1`) was not
the cause; it only sets `g.loggedIn = true` so the tab is reachable.

## Decoded backtrace

Built `display-v9` locally and ran the ESP32-S3 `addr2line` over the reported
addresses. Every frame resolves; line numbers match source exactly:

- `loop()` (`main.cpp:209`) -> `lv_timer_handler()` -> indev gesture handling
  -> `on_swipe_gesture` (`ui_shell.cpp:183`, so entry was via swipe)
  -> `ui_show_info()` (`:404`) -> `render_current()` (`:367`)
  -> `screen_info_show()` (`screen_info.cpp:217`) -> `info_render()` (`:159`)
  -> `ESP.getHeapSize()` (`Esp.cpp:136`) -> `heap_caps_get_info`
  -> `multi_heap_get_info_impl` -> stuck in `offset_to_block`.

`ESP.getHeapSize()` calls `heap_caps_get_info(..., MALLOC_CAP_INTERNAL)`, which
walks every TLSF heap block while holding the heap spinlock with interrupts
disabled. A corrupted block header turns that walk into an infinite loop, so
the Interrupt Watchdog fires. `ESP.getPsramSize()` walks the same way.
`ESP.getFreeHeap()` / `getFreePsram()` only read counters (O(1)) and are safe.

Only `/info` called the walking APIs, which is why only `/info` rebooted. The
tab-switching path itself is exonerated: all tabs share `render_current()`,
and the CPU was stuck above it in heap code, not in LVGL object code.

## Experiments and results

1. Commented out the heap and PSRAM gauge blocks in `info_render()`.
   Result: /info opens fine. Trigger confirmed.
2. Replaced the heap gauge with a CPU gauge (`100 - lv_timer_get_idle()`,
   LVGL's own O(1) busy measurement). Result: works.
3. Added a Mem gauge with the total snapshotted once via `ESP.getHeapSize()`
   at the end of `setup()`. Result: boot loop. The only new boot-path call was
   the snapshot, so the heap is very likely already corrupted by end of
   `setup()`. Mem gauge removed again; board boots correctly since.

## Current state of the code

- `screen_info.cpp`: gauges are Storage (static), CPU (LVGL busy %), plus the
  IP/Network/Firmware/DB tiles. No `ESP.get*` heap calls remain on this screen.
- `gauge_set()`: fixed flipped gradient. `lv_color_mix(c1, c2, mix)` returns
  `c1` at `mix=255`, so the old `mix(lo, hi, ...)` painted 100% green. Now
  `mix(hi, lo, ...)`: 0% green, 100% red.
- `serial_cmd.cpp`: new `MEM` command printing `free/min/maxblock` for heap
  and PSRAM using counter-only APIs. `min` is the low-water mark since boot
  (leak detector); `maxblock` flags fragmentation.
- `sim/Arduino.h`: ESP stub extended with the counter APIs used by `MEM`.

Audited all `strncpy`/`snprintf`/`memcpy` sites in `display-v9`; all are
bounded. The corrupter was not found by reading.

## How to monitor memory from here

- `MEM` over serial after boot (baseline), after each screen/flow, and across
  AP up/down cycles. Watch `min`; garbage values (near 2^32) mean the
  corruption is showing.
- `LV_USE_MEM_MONITOR 1` in `lv_conf.h` adds an overlay for LVGL's own 64 KB
  pool. That pool is separate from the system heap, so it tracks LVGL
  pressure only.
- Never call `getHeapSize()`/`getPsramSize()` outside a fresh-boot snapshot.
